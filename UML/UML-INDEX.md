## 2. OOAD Architectural Principles Reflected in the Project

### 1. Single Responsibility Principle (SRP)
- **Separation of FSM Logic**: Rather than embedding state transition rules within Next.js API route handlers, all 37 application states, transition legality matrices, and role authorization guards are strictly centralized in `lib/fsm.ts`.
- **Fee Calculation Decoupling**: Statutory calculations under Gazette GSR 516E are isolated in `lib/feeCalculator.ts`, which dynamically queries `FeeSchedule` records from the database instead of hardcoding figures.

### 2. State Pattern Implementation (Finite State Machine)
The core `Application` entity transitions through deterministic, legally mandated stages:
```
DRAFT ➔ SUBMITTED ➔ PAYMENT_PENDING ➔ PAYMENT_COMPLETED ➔ APPOINTMENT_BOOKED
  ➔ DOCUMENT_VERIFICATION ➔ DOCUMENT_VERIFIED ➔ POLICE_VERIFICATION_PENDING
  ➔ POLICE_VERIFICATION_COMPLETED ➔ OFFICER_REVIEW ➔ APPROVED ➔ PRINTING
  ➔ DISPATCHED ➔ DELIVERED
```
Illegal jumps (e.g. attempting to schedule an appointment before `PAYMENT_COMPLETED` or printing before `APPROVED`) are blocked at both compile-time and runtime.

### 3. Open/Closed Principle (OCP)
The catalog of citizen services (`PassportService`) and regional centres (`PassportCenter`) are completely database-driven. Adding new passport types (e.g. Diplomatic/Official) or new Post Office PSKs (POPSK) requires zero code modifications or redeployments.

### 4. Defense-in-Depth Security
- Password hashing with salted bcrypt (`bcryptjs`, 10 rounds).
- Account lockout policy: 5 consecutive failed attempts trigger a 30-minute lock (`lockedUntil` timestamp in `User` model).
- Mathematical and interactive Captcha challenges prevent automated bot attacks on registration and public status tracking.
- Every state transition generates an immutable record in `ApplicationStatusHistory` capturing the acting user ID, timestamps, and reason.
